# 10 人以内研发部门轻量承诺管理设计

日期：2026-08-09
状态：产品设计已确认，待实施计划
适用范围：10 人以内研发部门；月度定目标、每周承诺和更新；管理者定义月度结果，成员自主拆解周承诺；周承诺不逐条审核

## 1. 背景与问题

现有 AI Lab 系统已经具备目标、任务、证据、阻塞、成员、资产、绩效、提醒和报告能力，但当前用户体验仍偏向“研发管理台账 + 绩效与报表系统”：

- 页面直接显示 `Goal trajectory`、`Task composition`、`ACTIVE`、`CONFIRMED` 等英文标题和内部状态码；
- 管理者与成员共享过多相似页面，未围绕各自需要采取的行动组织信息；
- 月任务和周任务共用正式审核状态机，周任务必须审核后才进入目标进度；
- 绩效、报告、技术状态与每日管理事项并列，增加认知负担；
- 如果继续增加字段和审批，系统容易变成月底集中补录的填表工具。

本设计将系统定位为：

> 面向 10 人以内研发部门的轻量目标与承诺管理工作台，让正常工作低打扰，让偏差和阻塞自动浮现。

## 2. 第一性原理

部门管理系统必须持续回答六个问题：

1. 部门要获得什么结果？
2. 每项结果由谁负责？
3. 当前完成到什么程度，有什么事实？
4. 哪些事项已经偏离计划？
5. 现在需要谁作出什么决定？
6. 本周期学到了什么，如何进入下一周期？

对应的管理闭环为：

```text
目标 → 承诺 → 执行事实 → 异常暴露 → 管理决策 → 复盘沉淀
```

系统的价值不是增加录入量，而是降低信息差、缩短异常暴露时间、减少重复汇报，并让正式结论可追溯。

## 3. 已选方案

### 3.1 方案比较

#### 方案一：轻量承诺管理（采用）

管理者定义月度结果，成员自主拆解每周承诺；正常推进不写日报，只有异常、变化和交付需要更新；管理者审核月度结果，不逐条审核周任务。

优点：维护成本低、责任清晰、适合小团队。
代价：要求成员具备基本的自主规划能力，系统必须提供周末闭环提醒。

#### 方案二：强流程任务管理（不采用）

所有任务创建、状态变化和结果都经过审核。控制力强，但会使管理者成为审批瓶颈。

#### 方案三：汇报与报表优先（不采用）

月底集中补录并生成报告。实施阻力较低，但不能解决日常进度不透明问题。

### 3.2 明确非目标

- 不建设大型 OA 或多级审批平台；
- 不要求成员每日写日报；
- 不自动进行成员排名；
- 不用单一完成率替代管理判断；
- 不引入微服务或新的消息中间件；
- 不让普通成员操作模板、字典、校准和系统运维功能。

## 4. 角色与责任

### 4.1 管理者

- 定义部门目标、季度里程碑和月度重点结果；
- 为月度结果设置负责人、验收标准、截止日期和权重；
- 处理阻塞、延期、资源冲突和跨成员协同；
- 验收月度最终结果；
- 提供月度反馈并主持季度复盘；
- 维护敏感报告、关期和绩效治理边界。

### 4.2 成员

- 将本人月度结果拆解为每周承诺；
- 在出现阻塞、延期、范围变化或交付时更新事实；
- 周末关闭本人周承诺；
- 月末提交月度结果、说明和必要证据；
- 维护本人允许范围内的资产、知识产权、技能和协同记录。

### 4.3 业务线负责人（可选）

- 查看同业务线目标、异常、协同和资源，并协调责任人处理；
- 只维护本人的周承诺，不能替其他成员改写执行结果；
- 不读取无权访问的个人绩效或敏感报告；
- 不替代部门管理者进行关期、红线撤销和季度校准。

## 5. 管理节奏

### 5.1 月初：定义结果

- 部门原则上设置 5—10 项月度重点结果；
- 每名成员通常承担 1—3 项；
- 每项必须包含结果名称、验收标准、负责人、截止日期、目标权重和必要协同人；
- 禁止只写“推进、跟进、持续优化”等无法验收的描述。

### 5.2 周初：成员承诺

成员为本人月度结果创建每周 3—5 项承诺，每项只要求：

- 本周准备交付什么；
- 关联的月度结果；
- 计划日期；
- 是否需要协同。

成员从“新增本周承诺”提交时，在字段校验通过后直接以 `ACTIVE` 生效，不经过管理者逐条审批。`PLANNED` 只用于系统复制或转期生成的候选草稿，P0 不提供成员长期保存普通周承诺为草稿的入口；成员确认候选后才转为 `ACTIVE`。周初承诺截止后仍只有 `PLANNED` 或没有有效承诺时，系统生成“尚未完成本周承诺”待办，不能用草稿规避管理提醒。

### 5.3 周中：只更新变化

正常推进无需日报。只有以下情况需要更新：

- 新增阻塞；
- 预计延期；
- 交付范围发生变化；
- 需要管理者协调资源；
- 已形成可验证交付。

### 5.4 周末：成员自行闭环

成员必须将本周承诺标记为已完成或未完成。未完成必须填写原因及下一步；需要继续时，系统从原未完成事实幂等创建下一周承诺。成员不能直接取消已激活承诺。周承诺由成员自行关闭，不进入管理者审核队列。

### 5.5 月末：正式验收

成员提交月度结果，管理者确认：

- 是否达到验收标准；
- 证据是否成立；
- 未完成原因是否合理；
- 是否转入下月；
- 是否形成复盘或管理决策。

正式确认后，系统固化目标完成事实、绩效输入和报告快照。

## 6. 双层事实与计算合同

现有系统只读取 `CONFIRMED` 周任务计算目标进度，与“周承诺免审核”冲突。实施时必须分离执行事实和正式验收事实，并让 Dashboard、绩效和报告引用同一套命名合同。

### 6.1 三个正交维度

周承诺不能用一个状态同时表达执行、结果和风险。模型必须分成三个正交维度：

| 维度 | 字段/事实 | 允许值 | 含义 |
| --- | --- | --- | --- |
| 执行状态 | `execution_status` | `PLANNED/ACTIVE/SELF_DONE/SELF_UNDONE/CANCELLED` | 成员承诺当前处于哪个执行阶段 |
| 结果类型 | `result_status` | `DOING/EXCEEDED/ONTIME/DELAYED/UNDONE` | 完成时间和结果类型；`DELAYED` 表示已经完成但晚于计划 |
| 风险事实 | `lab_task_block_event` 及预计日期 | `OPEN/RESOLVED` 等 | 阻塞、预计延期和协同，不覆盖执行状态 |

“转下周/转下月”不是原任务的新终态。原任务必须保留 `SELF_UNDONE/UNDONE` 事实，再幂等创建带 `carried_from_id` 的新周期对象。`carried_from_id` 在目标周期内唯一，防止重复转期。

### 6.2 周承诺状态机

```text
PLANNED → ACTIVE → SELF_DONE
              ├→ SELF_UNDONE
              └→ CANCELLED（仅管理者因范围取消）
```

转换合同：

| 转换 | 操作者 | 前置条件和必填字段 |
| --- | --- | --- |
| `PLANNED → ACTIVE` | 负责人或管理者 | 已关联有效月度结果，计划日期有效 |
| `ACTIVE → SELF_DONE` | 负责人 | `actual_finish_time`、结果说明；关键承诺还需证据；结果类型只能为 `EXCEEDED/ONTIME/DELAYED` |
| `ACTIVE → SELF_UNDONE` | 负责人 | 未完成原因和下一步；结果类型固定为 `UNDONE` |
| `PLANNED/ACTIVE → CANCELLED` | 管理者 | 仅限月度范围变更或重复任务，必须填写取消原因；成员不能通过取消规避完成率 |
| `SELF_DONE/SELF_UNDONE → ACTIVE` | 负责人或管理者，关期前 | 必须填写纠错原因并写审计事件；当前行的 `result_status` 重置为 `DOING`，清空当前 `actual_finish_time/result_desc/fail_reason/next_action`，原值完整保留在执行事件中；既有证据保留但不视为本次有效提交 |

开放阻塞事件只能与 `ACTIVE` 并存。进入 `SELF_DONE/SELF_UNDONE/CANCELLED` 前必须在同一事务关闭开放阻塞事件并填写解决方式；解除阻塞只关闭事件，不自动改变执行状态。管理者覆盖成员执行状态时必须填写原因并写独立审计事件。关期后任何纠错必须先由管理者重新开放周期，并产生新修订。

### 6.3 月度结果状态机

```text
DRAFT → ACTIVE → PENDING_REVIEW → CONFIRMED
                         └→ ACTIVE（退回）
```

转换合同：

| 转换 | 操作者 | 前置条件和必填字段 |
| --- | --- | --- |
| `DRAFT → ACTIVE` | 管理者 | 验收标准、负责人、截止日期和权重完整 |
| `ACTIVE → PENDING_REVIEW` | 负责人 | 完成时提交结果说明和证据；未完成时提交原因和下一步 |
| `PENDING_REVIEW → CONFIRMED` | 有审核权限且不是负责人的人员 | 验收意见、验收人、验收时间和证据版本固化；允许确认 `UNDONE` 事实 |
| `PENDING_REVIEW → ACTIVE` | 审核人 | 必须填写退回原因；原提交和退回记录保留 |
| `CONFIRMED → ACTIVE` | 管理者 | 必须填写重开原因；已关期时先重开周期并生成新的绩效修订 |

月度结果转下月时，原月结果必须先以 `CONFIRMED + UNDONE` 固化，再创建带 `carried_from_id` 的新月结果，不能修改原周期归属。

### 6.4 执行进展公式

执行进展是管理信号，不是绩效或正式目标完成率。

在口径日期 `asOf` 下，某月度结果的到期承诺集合 `E` 为：

- 直接关联该月度结果；
- 已在 `asOf` 前激活；
- `plan_date <= asOf`；
- 不包含由管理者因月度范围变更而取消的 `CANCELLED`；
- 由成员主动放弃的事项必须记为 `SELF_UNDONE`，不能排除。

完成集合 `D` 为 `E` 中 `execution_status=SELF_DONE` 的承诺。

```text
周承诺执行率 = |D| / |E| × 100%
```

若 `E` 为空，界面显示“暂无到期承诺”，不能显示 0% 或 100%。承诺不设置权重，执行率只用于发现偏差；系统同时展示 `已完成数/到期承诺数/阻塞数/未完成数`，防止成员通过拆分任务操纵单一百分比。

目标健康度使用“运营进展”，不得冒充正式进展。月度结果的运营系数为：已确认结果采用正式结果系数；尚在执行或待验收时，若存在到期承诺则采用周承诺执行率，否则为 0 并标记“尚未拆解到期承诺”。里程碑和年度运营进展仍分别按 `goal_weight` 和季度 `weight` 聚合。期望进展继续按 `plan_date <= asOf` 的计划到期权重累计，健康颜色沿用现有 5/15 个百分点偏差及阻塞/逾期最严重值规则。

因此 Dashboard 必须分别命名“运营进展”和“已验收进展”；只有运营进展用于实时健康预警，只有已验收进展进入正式结果和绩效。

跨月 ISO 周按月度父任务归属，不按周起止日期归属：周承诺的 `parent_id` 决定唯一月份，`plan_date` 必须落在父月内；允许自然周跨月，不复制到两个周期。

### 6.5 正式进展与绩效公式

正式进展只读取已确认月度结果：

```text
正式结果系数 = 1，result_status ∈ {EXCEEDED, ONTIME, DELAYED}
正式结果系数 = 0，result_status = UNDONE
里程碑正式进展 = Σ(月度结果 goal_weight × 正式结果系数) / 100
年度正式进展 = Σ(季度里程碑 weight × 里程碑正式进展) / 100
```

里程碑下月度结果的 `goal_weight`、成员当月重点结果的 `perf_weight`、年度目标下季度里程碑的 `weight` 都必须在激活前分别校验合计为 100；权重不完整时只能保存草稿，不能进入正式计算。

绩效继续使用现有已确认月度重点任务的 `perf_weight` 和结果系数，不读取周承诺执行状态。截止关期仍未验收的月度结果只在关期快照中按 `UNDONE` 计入，不能伪造审核人或把源任务状态改成 `CONFIRMED`。

### 6.6 正式验收快照

正式验收和关期至少固化：月度结果 ID/版本、父目标和里程碑、负责人和业务线、`goal_weight`、`perf_weight`、结果类型、结果说明、证据 ID/版本/审核状态、验收人/时间/意见、关期截止时间和修订号。

Dashboard 同时展示：

- 执行进展：成员周承诺形成的管理信号；
- 已验收进展：管理者确认月度结果形成的正式进度。

两个百分比必须使用上述统一公式，不得由不同页面自行解释。单次 Dashboard 响应分别返回实时投影的 `executionAsOf`，以及正式事实的 `formalRevision/closeRevision`；查询事务保证二者来自同一响应读取点，但不得谎称实时事件和关期快照具有相同修订号。

### 6.7 执行状态历史

`execution_status` 是当前状态缓存，每次转换必须追加不可覆盖的执行事件，至少记录任务 ID、前后状态、结果类型、实际完成时间、操作者、操作时间、原因、任务版本和关联证据版本。纠错、取消和转期不能覆盖原事件。

工作台读取当前状态，审计、迁移验证、关期和争议处理同时读取事件链；当前状态与最后一条事件不一致时拒绝关期并进入数据修复队列。

## 7. 任务层级与最小字段

管理层保留四层结构：

```text
年度方向
└─ 季度里程碑
   └─ 月度重点结果
      └─ 本周承诺
```

普通成员默认只操作“我的月度结果”和“我的本周承诺”；年度与季度映射由系统带入。

### 7.1 月度重点结果

最小字段：结果名称、验收标准、负责人、完成日期、目标权重、必要协同人。

### 7.2 本周承诺

最小字段：交付内容、关联月度结果、计划日期、协同需求。

成员不填写绩效权重、目标权重或主观完成百分比。权重只存在于月度重点结果。

### 7.3 证据分级

- 普通周承诺：一句结果说明即可；
- 关键周承诺：结果说明和链接；
- 月度重点交付：必须提供可验证证据；
- 涉及质量门禁、绩效或正式验收：证据必须按现有审核规则确认。

## 8. 信息架构与工作台

主导航按管理动作组织：

1. 工作台；
2. 目标与执行；
3. 团队与能力；
4. 资产与成果；
5. 绩效与报告。

### 8.1 管理者工作台

#### 今日需要我处理

- 新增阻塞；
- 预计延期；
- 待验收月度结果；
- 资源协调请求；
- 超过约定时间未更新的重点任务；
- 尚未完成的管理决策。

#### 本月目标态势

- 本月重点结果总数；
- 正常、存在风险和已经偏离的数量；
- 负责人、执行进展、已验收进展和下一交付日期；
- 可下钻到周承诺、异常和证据。

#### 团队承诺与负载

- 每人月度重点结果；
- 本周承诺数量；
- 阻塞、延期和协同数量；
- 明显过载或没有重点任务的成员。

不生成不可解释的人员综合排名。

#### 周会工作区

- 上周承诺完成情况；
- 未完成原因；
- 本周新承诺；
- 待决策问题；
- 决策内容、责任人和截止日期。

### 8.2 成员工作台

- 我的月度结果；
- 本周承诺；
- 即将到期事项；
- 当前阻塞和协同请求；
- 待补结果说明或证据；
- 管理者反馈。

核心快捷操作仅保留：新增本周承诺、报告阻塞、提交交付结果。

### 8.3 业务线负责人工作台

- 本线目标和异常；
- 同线成员负载；
- 跨线协同；
- 本线待处理事项。

所有数据由服务端可信角色和业务线范围裁剪。

## 9. 管理决策记录

新增独立管理决策概念，不使用普通任务备注替代。记录字段包括：

- 问题；
- 决策内容；
- 责任人；
- 截止日期；
- 关联目标或任务；
- 完成状态；
- 创建人与时间。

未完成决策自动进入下一次周会工作区。

## 10. 中文化设计

数据库和接口保留稳定英文代码，界面统一展示中文业务词汇。

中文化覆盖：

1. 菜单、卡片、按钮和帮助文本；
2. 状态、角色、业务线和操作名称；
3. 提醒、任务、成员和报告演示数据；
4. Markdown、Word 和 PDF 输出；
5. 空状态、错误提示和审核说明。

示例映射：

| 内部代码/现有文本 | 中文展示 |
| --- | --- |
| `ACTIVE` | 进行中 |
| `PENDING_REVIEW` | 待验收/已提交（按对象类型） |
| `CONFIRMED` | 已确认 |
| `UNDONE` | 未完成 |
| `RED_LINE` | 触发红线 |
| `Goal trajectory` | 目标进度趋势 |
| `Task composition` | 任务状态分布 |
| `Capacity ledger` | 团队负载 |
| `Personal inbox` | 我的待办 |

同一内部代码可根据月度结果或周承诺的业务语境展示不同中文，但映射必须由统一词典维护，不得散落在页面中。

## 11. 技术结构

继续使用现有 Vue 2 + Spring Boot + MySQL + Redis 模块化单体。

### 11.1 任务域

月度结果保留正式审核工作流；周承诺必须使用独立 `execution_status` 字段，避免继续重载 `workflow_status` 的语义。

历史周任务不得只按 `workflow_status` 迁移，必须按 `(workflow_status, result_status, actual_finish_time, period_lock_flag, has_open_block)` 组合推导：

| 原组合 | 新执行状态 | 处理 |
| --- | --- | --- |
| `DRAFT + DOING/NULL + actual_finish_time IS NULL` | `PLANNED` | 保留原字段 |
| `ACTIVE + DOING/NULL + actual_finish_time IS NULL` | `ACTIVE` | 开放阻塞仍由事件表表达 |
| `PENDING_REVIEW + EXCEEDED/ONTIME/DELAYED + actual_finish_time + 无开放阻塞` | `SELF_DONE` | 保留待审提交和证据元数据 |
| `PENDING_REVIEW + UNDONE + 无开放阻塞` | `SELF_UNDONE` | 保留未完成原因和下一步 |
| `CONFIRMED + EXCEEDED/ONTIME/DELAYED + actual_finish_time + 无开放阻塞` | `SELF_DONE` | 保留原审核人、证据和完成类型 |
| `CONFIRMED + UNDONE + 无开放阻塞` | `SELF_UNDONE` | 不得错误映射成完成，保留原审核人 |
| 任一终态候选 + 开放阻塞 | 不自动迁移 | 违反新终态不变量，进入隔离清单，不得生成终态执行状态 |
| `ACTIVE/DRAFT + 终态结果` | 不自动迁移 | 可能来自审核退回或历史异常，进入隔离清单人工核对 |
| 其他无法解释组合 | 不自动迁移 | 阻断切换，不得默认成 `SELF_DONE` |

`period_lock_flag` 只决定是否允许修改，不改变结果含义。迁移采用新增影子列和分批事务，不覆盖旧 `workflow_status`、`result_status`、证据审核、操作日志或关期快照。

对于“终态候选 + 开放阻塞”的隔离记录，管理者必须逐条选择并留下迁移审计：若阻塞在终态时确实仍未解决，先将原 episode 事实写入迁移快照，再以 `MIGRATION_TERMINAL_UNRESOLVED` 代码在迁移截止时间关闭；若属于历史漏关，则填写纠错原因后关闭。只有不存在开放 episode 后才允许重新运行确定性映射。迁移程序不得自行推测阻塞已经解决。

迁移必须满足：

- 仅回填 `execution_status is null` 的周任务，重复执行结果不变；
- 迁移前后按原状态组合和新执行状态核对分组计数；
- 发现隔离记录时不得启用新计算口径；
- 上线切换前保留字段、统计快照和功能开关；
- 月度任务不参与本次执行状态回填；
- 任何回滚不得反向改写历史审核事实。

切换分为三个阶段：

1. 扩展阶段：新增字段、事件表和迁移程序；旧工作流仍为唯一写入口，完成历史回填和双口径只读比对；
2. 读切换阶段：Dashboard、提醒、工作台、关期和报告全部切换到新合同，但尚未开放成员自闭环；此阶段可以冻结写入后切回旧版本；
3. 写切换阶段：启用成员 `SELF_DONE/SELF_UNDONE` 写入。第一条新执行事件写入后即越过不可回滚点，禁止把应用切回只识别 `workflow_status=CONFIRMED` 的旧读模型；故障只能关闭新写入口、保留数据并向前修复。

若组织要求写切换后仍可版本回退，必须在上线前提供经过黄金值验证的旧版兼容读取层；该兼容层只能投影计算结果，不能伪造 `CONFIRMED`、审核人或证据审核事实。

### 11.2 工作台查询层

新增角色化工作台查询服务，一次返回当前用户可见的行动、目标、承诺和风险。不得依赖前端请求多个宽列表后自行裁剪权限。

### 11.3 展示词典

建立统一状态描述 DTO 或前端词典模块，包含代码、中文名称、说明、下一步动作、颜色和风险级别。Dashboard、列表、详情、通知和报告共用相同定义。

### 11.4 数据流

```text
管理者发布月度结果
        ↓
成员创建周承诺
        ↓
成员提交完成或异常事实
        ↓
工作台聚合执行进展
        ↓
管理者验收月度结果
        ↓
固化绩效事实和报告快照
```

周承诺不得直接生成正式绩效结论。

### 11.5 报告数据源分级

报告预览可以读取实时事实；报告定稿必须在周期已关闭后生成，并固定关期修订、绩效修订、模板修订、数据截止时间和源事实版本。Provider 按用途分级：

| Provider | 分级 | 定稿口径 |
| --- | --- | --- |
| `GOAL_PROGRESS` | `FORMAL_SNAPSHOT` | 只读正式进展快照 |
| `TASK_DETAIL` | `FORMAL_CLOSE_SNAPSHOT` | 读取关期锁定的月结果和子周承诺，明确区分正式结果与成员自报执行事实 |
| `TASK_STAT` | `FORMAL_CLOSE_SNAPSHOT` | 按关期快照统计，不查询关期后的实时变更 |
| `TASK_UNDONE` | `FORMAL_CLOSE_SNAPSHOT` | 包含关期时正式未完成和未验收按未完成处理的对象 |
| `PERF_SUMMARY` | `FORMAL_SNAPSHOT` | 固定绩效修订，只读正式验收事实 |
| `TASK_NEXT` | `CONTEXT_SNAPSHOT` | 下一周期计划，仅作上下文，不计入本期绩效 |
| `TASK_COORD` | `CONTEXT_SNAPSHOT` | 截止时间点协同事实，生成后固化 |
| `TASK_BLOCK` | `CONTEXT_SNAPSHOT` | 截止时间点开放阻塞事实，生成后固化 |
| `ASSET_SUMMARY` | `CONTEXT_SNAPSHOT` | 截止时间点资产风险，生成后固化 |
| `IPR_SUMMARY` | `CONTEXT_SNAPSHOT` | 截止时间点知识产权事实，生成后固化 |
| `MANUAL_SUMMARY` | `MANUAL_REVISION` | 固定人工小结修订号 |

`CONTEXT_SNAPSHOT` 可以进入定稿报告，但必须标注“截至某时点”，且不能参与正式目标或绩效公式。定稿后所有章节只读取实例内固化内容，重开周期只能生成新报告版本，不能改变旧报告。

P0 必须同步适配报告读取和定稿门禁；若尚未完成，P0 环境必须禁用报告定稿，不能继续按旧 Provider 口径生成正式报告。

## 12. 权限边界

权限按资源、动作和字段校验，不能只按角色或菜单描述：

| 资源/动作 | 管理者 | 业务线负责人 | 成员 |
| --- | --- | --- | --- |
| 年度目标/季度里程碑创建与定义字段修改 | 全部门 | 只读，除非另授目标管理权限 | 只读公开字段 |
| 月度结果创建、负责人/验收标准/权重/截止日期修改 | 全部门；激活后变更必须有原因 | 只读或提出变更，不得修改权重 | 只读本人月度定义字段 |
| 月度结果执行说明和提交验收 | 作为负责人时仅能提交 | 同线本人或授权对象提交 | 仅本人提交 |
| 月度结果正式验收 | 有审核权限且审核人不能等于负责人 | 仅显式授予审核权限、同线且非负责人 | 不允许 |
| 周承诺创建与执行 | 可管理全部门，覆盖成员结果必须有原因和审计 | 仅维护本人；可查看同线并发起协同，不得改写他人执行状态 | 仅本人；激活后不得修改父月、负责人和业务线 |
| 周承诺取消 | 仅管理者因范围变更取消 | 只能提出取消请求 | 不允许直接取消，无法完成时记 `SELF_UNDONE` |
| 绩效、关期和红线治理 | 全部门且遵循现有独立敏感权限 | 不允许校准、关期或撤销红线 | 仅查看本人允许反馈 |
| 报告列表/下载 | 全部门；敏感报告仍需独立权限 | `ALL` 或本人业务线的非敏感定稿报告 | `ALL` 或本人业务线的非敏感定稿报告 |

管理者本人作为月度结果负责人时不得自我验收，必须由另一名具有审核权限且非负责人的管理者或受托业务线负责人验收。启用正式月度结果前，系统配置检查必须确认至少存在两名可形成独立验收关系的有效用户；不存在合格审核人时，禁止激活该管理者负责的月度结果，也禁止进入关期，而不是在关期时把它按 `UNDONE` 或“排除绩效”临时处理。

字段级授权要求 Service 拒绝越权提交的 `owner_id`、`biz_line`、`parent_id`、权重、验收标准和关期字段；Mapper 查询同时按可信成员身份和业务线范围裁剪。前端隐藏按钮只改善体验，不能作为授权边界。

历史快照不能作为当前授权来源。报告列表、详情和下载必须根据当前可信角色、业务线、报告 `biz_line` 和敏感权限重新授权；`biz_line=ALL` 的非敏感定稿报告可按组织政策开放给全员。

## 13. 失败与边界处理

- 周承诺未关联月度结果：拒绝创建；
- 周末未关闭：进入本人待办，不自动标记完成；
- 预计延期或新增阻塞：立即进入相应管理者异常队列；
- 月度结果被退回：保留提交记录、退回人和退回原因；
- 多人并发编辑：使用现有乐观锁提示数据已变化，不静默覆盖；
- 通知失败：保存业务事实，提醒任务可重试；
- Dashboard 聚合失败：显示明确失败和重试入口，不把错误展示为空数据；
- 报告生成失败：保留已成功制品和用户可理解的错误摘要。

### 13.1 跨月周

允许 ISO 自然周跨月。每条周承诺只归属于一个父月度结果，以 `parent_id` 和 `plan_date` 决定唯一月份；周标签仅用于工作节奏。跨月周不得复制进两个周期，也不得因为周一和周日不在同月而拒绝创建。

### 13.2 关期锁定

月关期必须同时锁定：

- 本月月度结果；
- 通过 `parent_id` 关联的全部周承诺，不论其 `period=YYYY-Www`；
- 相关结果、证据、质量门禁、阻塞事件和协同事实；
- 关期形成的绩效和正式进展快照。

关期事务先处理仍开放的子周承诺阻塞事件：把“截止时仍未解决”事实写入关期快照，再以明确的 `PERIOD_CLOSED_UNRESOLVED` 解决代码关闭原 episode；如果事项转入下期，则在新承诺上创建带 `carried_from_event_id` 的新开放 episode。提醒扫描只处理当前开放周期、未锁任务的开放事件，不能继续为已关期源任务生成 7/14 天提醒。

锁顺序固定为：周期关期记录 → 月度结果 → 子周承诺 → 证据/质量/阻塞/协同 → 绩效快照。任务更新、月度验收和报告生成必须使用相同顺序或在遇到关期版本变化时失败重试，避免并发死锁和跨截止时间混读。

关期后源数据只读；纠错必须先由管理者重开周期、填写原因并产生新修订。重开不能修改旧绩效快照或旧定稿报告。

### 13.3 并发结果

- 周承诺更新与关期并发：关期取得锁后，晚到更新失败并提示“周期已关闭”；
- 月度验收与关期并发：只有在关期截止前完整提交并成功加锁的验收进入本次快照；
- 报告生成与重开并发：报告固定读取已选择的关期修订；修订变化时终止当前定稿并要求重新生成；
- 转期重复请求：依靠 `carried_from_id + target_period` 唯一约束返回同一新对象；
- 乐观锁冲突：保留用户输入并提示刷新差异，不能静默采用最后写入。

## 14. 验收标准

### 14.1 使用效率

- 成员能在 3 分钟内创建或更新一周 3—5 项承诺；
- 成员每周常规维护时间控制在 10 分钟以内；
- 管理者能在 5 分钟内识别本周必须干预的事项；
- 正常任务无需每日重复填报。

### 14.2 业务正确性

- 周承诺完成无需管理者审批；
- 月度结果必须由管理者正式确认；
- 执行进展和已验收进展分开计算、分开展示；
- 阻塞和延期进入正确管理者的行动队列；
- 周承诺不能绕过月度结果形成正式绩效；
- 月报正式章节只读取关期/绩效快照，上下文章节读取带截止时间并固化的事实；
- 未关期周期不能定稿报告；重开后旧报告内容不变；
- 历史状态迁移后进度与审计信息一致。

### 14.3 权限与体验

- 普通成员不能读取他人绩效和敏感报告；
- 业务线负责人不能越过可信业务线范围；
- 普通业务页面不显示内部英文状态码；
- 所有错误、空状态和下一步操作使用明确中文；
- 管理者与成员登录后进入各自工作台。

### 14.4 测试策略

- 状态机单元测试：每条允许和拒绝的周承诺/月度结果转换，包含退回、纠错、取消、转期和终态重开；
- 计算黄金值测试：同一固定数据集下，Dashboard 执行率、正式进展、绩效和报告数字必须符合第 6 节公式；
- 权限测试：篡改 `owner_id/biz_line/parent_id/weight` 的对象级越权、管理者自审、同线审核和报告列表/下载；
- 迁移组合测试：覆盖 `workflow_status × result_status × actual_finish_time × period_lock_flag × has_open_block`，至少包含 `CONFIRMED+UNDONE`、退回后的 `ACTIVE+终态结果`、终态候选+开放阻塞隔离/人工关闭/重跑、已锁周期、异常隔离和重复执行；
- 迁移计数测试：迁移前后组合分组总数一致，旧工作流、审核人、证据和日志不变；
- 并发测试：周更新与关期、月验收与关期、报告生成与重开、重复转期；
- 切换测试：扩展、读切换和写切换三个阶段；写切换前冻结写可回退，写切换后旧版本启动必须被功能开关拒绝且新执行事件不丢失；
- 周期测试：ISO 自然周跨月时只归属一个父月，并随父月关期锁定；
- 阻塞关期测试：截止时开放事件进入快照、源 episode 停止提醒、转期新 episode 继承来源且只对新对象继续升级；
- 报告测试：Provider 分级、未关期不可定稿、绩效/关期修订 pin、重开后旧快照不变；
- 工作台测试：异常、待办、分页总数和下钻筛选精确一致；
- 中文化静态合同：按对象类型检查状态词典，并设置允许技术词清单，避免误伤交付物中的代码、链接和必要英文；
- 端到端验收：真实角色完成月初发布、周承诺、自主关闭、阻塞、月末验收、关期和报告生成。

## 16. 成功指标

不以录入条数评价系统。上线首月只建立基线，从第二个月开始连续观察三个完整月度周期：

| 指标 | 数据来源和口径 | 三周期目标 |
| --- | --- | --- |
| 成员每周维护时间 | 前端记录有业务操作的会话时长，排除超过 5 分钟无操作的空闲时间 | 中位数 ≤ 10 分钟，P90 ≤ 20 分钟 |
| 创建本周承诺耗时 | 从打开创建入口到成功提交 3—5 项承诺的可用性测试 | 中位数 ≤ 3 分钟 |
| 管理者定位异常耗时 | 给定真实工作台，由管理者找出全部需介入事项的任务测试 | P90 ≤ 5 分钟，且无漏项 |
| 周承诺按时闭环率 | 截止下一个工作日已进入 `SELF_DONE/SELF_UNDONE` 的承诺 / 第 6.4 节到期集合 `E`；合法管理者取消项按同一合同排除 | ≥ 90% |
| 阻塞升级 SLA | 开放阻塞在 7/14 天阈值后一个扫描周期内生成正确接收人提醒的比例 | 100% |
| 正式结果证据覆盖率 | `CONFIRMED + EXCEEDED/ONTIME/DELAYED` 的月度重点结果中具有满足规则的可追溯证据比例；`CONFIRMED+UNDONE` 不进入该分母，但必须具备原因和下一步 | ≥ 95% |
